# 更新后出现 RAM 余量报错：反馈排查 · 2026-10-26

实施顺序、批次范围与验收标准见[内存保护与缓存协调优化清单](RAM_HEADROOM_OPTIMIZATION_CHECKLIST_20261026.md)。

后续状态：用户授权完成 M1～M9 后，已实现并通过本机定向验收，见[实施记录](RAM_HEADROOM_IMPLEMENTATION_20261026.md)。以下排查公式、报错和建议保留修复前的历史口径；当前普通预留已封顶 4 GiB。

## 结论与边界

输入是一张用户评论截图，提示 `MemoryError`、预计需要 `256 MiB`、预留后可用 `0 MiB`。尚无受影响机器的版本、素材参数及报错时内存快照。

- 已定位到程序主动抛出的准入错误；这段提示本身不能证明 Windows 分配内存失败，也不能证明显存不足。
- 对比本地 `v3.0.2` 与 `v3.0.4` 标签，相关默认值相同。没有发现此次更新调大预览缓存、解码队列、在途数或默认启用自动预渲染。
- `v3.0.3` 发布准备之前增加了帧分配前、运行中及空闲工作进程的余量检查；`v3.0.4` 保留了这些检查。旧版能够继续执行的压力区间，新版会主动停止。
- 已用模拟快照复现：缓存预算允许保留的状态可以同时被处理准入拒绝。这是独立于用户现场的可复现策略冲突，是本次反馈的候选原因。
- 单凭截图不能区分该冲突、其他程序占用、提交余量不足或程序自身持续增长。不能据此宣称所有用户都属于误报，或先关闭保护。

最初排查阶段只做诊断及记录；随后授权的源码实施与验收按上方链接单独记录。

## 触发条件

源码：[memory_budget.py](../../dlss5tool/memory_budget.py)。

```text
预留 = max(2 GiB, 总物理内存 / 8)
可用于新增处理的余量 = max(0, min(可用物理内存, 可用提交空间) - 预留)
已知所需字节数 > 余量 → 主动抛出 MemoryError
```

因此“0 MiB”是扣除预留后的数字，不是操作系统报告的真实可用 RAM。即使提交空间充足，以下情况都会产生截图中的同一条提示：

| 总 RAM | 实际可用 RAM | 预留 | 提示中的可用量 |
| --- | --- | --- | --- |
| 8 GiB | 2 GiB | 2 GiB | 0 MiB |
| 16 GiB | 2 GiB | 2 GiB | 0 MiB |
| 32 GiB | 4 GiB | 4 GiB | 0 MiB |
| 64 GiB | 8 GiB | 8 GiB | 0 MiB |
| 128 GiB | 16 GiB | 16 GiB | 0 MiB |

模拟 32 GiB RAM、可用物理内存 12 GiB、可用提交空间 3 GiB，同样得到 0 MiB。现有提示没有区分物理内存限制和提交空间限制。

`256 MiB` 是本次检查收到的缓冲需求估算，不是固定内存上限，也不是缓存设置。多个入口调用该检查，不能仅凭这个数反推出素材尺寸、HDR 或具体处理阶段。

`receive_worker_command()` 每 0.5 秒检查一次空闲 worker，并在收到非停止命令时检查。即使暂停预览，工作进程也可能因系统余量下降而退出；随后消费其错误时才在界面上看到报错。

## 缓存与处理准入冲突复现

`cache_limit_bytes()` 与 `memory_headroom_bytes()` 使用同一预留线；前者允许缓存占到线边，后者要求处理缓冲仍在线外另有空间。

模拟过程不创建大型数组，不消耗真实压力内存：

1. 总 RAM 16 GiB；可用 RAM 4 GiB；可用提交空间 16 GiB；已有缓存 2 GiB；保存预算 8 GiB。
2. 缓存许可总量为 `min(8, 16/4, 2+4-2) = 4 GiB`。
3. 假设缓存增长到允许的 4 GiB，可用物理内存降至 2 GiB，可用提交空间降至 14 GiB。
4. 此时缓存许可仍为 4 GiB，无须按当前缓存规则收缩；处理余量却为 0。
5. 调用 `require_memory_headroom(256 * 1024**2)`，得到与截图完全相同的中文提示。

最小重现（仓库根目录，复用 `.venv`，加 `-B`）：

```python
from unittest import mock
from dlss5tool import memory_budget as mb

GIB = 1024**3
state = dict(total_physical_bytes=16*GIB,
             free_physical_bytes=2*GIB, free_commit_bytes=14*GIB)
assert mb.cache_limit_bytes(8*GIB, 4*GIB, memory=state) == 4*GIB
assert mb.memory_headroom_bytes(memory=state) == 0
with mock.patch.object(mb, 'system_memory', return_value=state):
    mb.require_memory_headroom(256*1024**2)  # 主动抛出目标提示
```

清缓存暂时释放了空间，可以帮助判断是否与该路径有关；它也会释放其他会话资源，因此成功重试仍不能单独证明冲突是唯一原因。导出前 `_begin_export_ui()` 会停预取，但不会统一清空可复用预览缓存，已有缓存可能继续占用空间。

## 强制检查大小评估（后续问答补充）

当前数值是项目自己的保守策略，已有测试验证策略按预期执行；本轮未发现按不同 RAM 容量、模型及驱动实际峰值标定这些阈值的证据。作为缓存收缩线有合理用途，直接作为所有阶段的停止线则偏保守。

对于截图中的 256 MiB 新增需求，当前要求物理可用量和当前进程可提交量都至少达到下表数值：

| 总 RAM | 项目预留 | 通过 256 MiB 检查所需的各项余量 |
| --- | --- | --- |
| 8 / 16 GiB | 2 GiB | 2.25 GiB |
| 32 GiB | 4 GiB | 4.25 GiB |
| 64 GiB | 8 GiB | 8.25 GiB |
| 128 GiB | 16 GiB | 16.25 GiB |

它不依据当次模型或素材工作区决定系统预留，大内存机器的拒绝线会随总容量持续增长。预留不是实际申请的内存，多次调用检查也不意味着每次又分配一份预留。

另有两处会放大保守程度：

- 部分 GUI/VSR 入口把 `known_ram * 1.20 + 512 MiB` 这一推荐量用于强制准入，而通用导出使用启用阶段的已知缓冲量，检查口径不同。推荐余量与必要新增分配应分开表达。
- GUI `_export_hdr_video()` 在 `scale=1` 时调用 `estimate_resources()` 未传 `use_super_resolution=False`，但仅在 `scale>1` 时创建超分会话，估算包含未启用的 VSR 缓冲。4K HDR、1 倍、1 槽的纯估算对比：默认已知量 569.53125 MiB、推荐量 1195.4375 MiB；排除 VSR 后为 379.6875 / 967.625 MiB。推荐量相差 227.8125 MiB。这个算例不等于整个导出进程峰值，解码/编码等需求仍须计入。

空闲 worker 还会按两帧需求周期检查，虽然当时没有新命令需要执行。它可以用于主动退役保护，但不能理解为证明当前马上要分配两帧，宜与正常任务分配失败采用不同的恢复和提示。

建议先修复阶段估算与缓存让路，把推荐值用于预警，强制检查按尚未分配的必要峰值加经实测确认的安全余量计算。系统预留是否降值、是否封顶，需在修正口径后以代表性任务实测决定；本轮没有直接改为另一个未经验证的固定数字。

Windows `ullAvailPhys` 是可立即复用的物理内存，`ullAvailPageFile` 是当前进程还能提交的最大内存，不一定等于系统全局提交余量；若需要系统级数据，微软建议由 `GetPerformanceInfo` 的 `CommitLimit - CommitTotal` 求取。诊断命名和硬检查应保留这一区别。来源：[Microsoft MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)。

补充验证仍使用 `.venv/Scripts/python.exe -B -`，仅调用资源估算函数，未启动 GUI/原生处理任务，无新增临时文件。

## 策略冲突的协调方案（对齐时建议，实现见实施记录）

建议扩展现有 `SharedCacheBudget`，让缓存收缩与即将发生的处理分配共享准入口径。现有 `demand` 是待缓存帧的最低需求，不能直接复用为处理额度，否则会把两个不同含义混在一起；扩展共享结构时要更新版本并校验布局。

### 1. 分清额度的归属和状态

- 区分可回收缓存、仍被当前处理引用的帧、尚未分配的处理峰值，以及系统安全底线。
- 处理者按阶段登记待分配额度，由唯一所有者持有；同一缓冲不能被 GUI、宿主及子进程分别登记为三份新增需求。
- 对重叠执行的阶段，应覆盖可能同时存在的峰值；互斥阶段不能简单累加。已分配内存已经体现在 OS 快照中，不再作为待分配需求扣第二次。
- 分配完成时更新额度状态，取消或异常时归还未使用额度。活跃资源仍由原所有者负责释放，账本清零不代表实际内存已经释放。
- 在互斥锁内发布和核算额度，分配、跨进程等待及回收操作放在锁外。它只能协调本工具的已登记需求，不能防止外部程序突然占用内存。

### 2. 在真正分配之前完成有界回收

流程：`登记处理需求 → 限制缓存增长并暂停额外预取 → 各所有者回收并确认 → 获取新快照 → 重新检查 → 分配或报告不足`。

- 保留正在消费的帧和必要时序状态，优先丢弃远离播放位置的帧及可重建的原始推理缓存。
- 回收请求使用代次和确认状态，避免光流子进程尚未响应时宿主已经先退出。等待有截止时间并可取消，不能在全局锁内等待。
- 最终检查应绕过 250 ms 缓存取新快照；不能把“申请回收的字节数”直接加回可用量。数组仍被其他引用持有或分配器未归还时，额度下降不一定等于物理内存上升。
- 恢复只重试尚未开始的准入/分配；不自动重跑已执行的原生处理、写出或改变时序历史。

### 3. 给当前任务确定的优先级

当前帧和已启动导出的必要缓冲优先于后台预取。任务的待分配额度有效期间，各缓存入口都必须遵守收缩目标，避免刚回收又被另一个缓存填回。导出所需的既有缓存仍可复用，不要求每次导出统一清空。

例如总 RAM 16 GiB、可用 RAM 2 GiB、已有可回收缓存 4 GiB，沿用系统底线 2 GiB，下一阶段还需要 256 MiB：先回收至少 256 MiB 再加必要波动余量并确认实际余量，才有可能通过检查。前提是可提交量也充足，且待回收数据没有被活跃处理继续持有。这个方案先解决已复现冲突，不依赖降低当前系统底线。

### 4. 区分正常波动、回收和严重压力

增加“正常／回收中／仍不足”的状态，并让恢复预取的余量高于进入回收的余量，避免边界反复填充与清空。空闲 worker 应先参与回收协调；严重压力仍允许及时退役，不能把尚无新分配命令的空闲检查当作普通帧分配失败。退役后保留明确原因和恢复入口，不静默重建时序会话。

### 5. 首轮验证边界

先保持现有系统安全底线，完成阶段估算纠错、处理额度、回收确认及失败瞬间诊断。定向验证：缓存满后可继续分配、两个处理者竞争、暂停期间跨进程回收、仍被引用的缓存无法实际释放、提交量不足、回收超时、取消/异常归还额度，以及严重压力仍能安全停止。

系统底线的封顶或降值另结合代表性任务实际峰值校准。此方案不承诺消除驱动、模型或外部程序造成的所有内存压力。

## 现场核对与后续修复方向

- 获取报错版本、总内存、打开素材/预览/导出的具体时机，以及报错后尽快导出的诊断报告。现有报告上下文已有 `system_memory` 的总 RAM、可用 RAM、可用提交空间及相关设置；它是导出时快照，不一定等于报错瞬间。
- 可先点击清除预览缓存，再将预览缓存预算暂设为 1024～2048 MiB 重试。这只降低可复用缓存容量，具体是否有效依赖现场余量；不要以恢复默认设置作为首选，因为默认缓存上限反而是 8192 MiB。
- 修复应优先协调缓存回收和即将执行的处理需求，使缓存为必要缓冲让出空间；同时在错误发生时记录原始可用量、提交余量、预留和具体阶段，改善现有统一提示。
- 是否调整处理阶段预留，需要结合已知工作区、共享池所有权、暂停及跨进程行为验证。此前原生长期增长尚未结案，不能通过移除保护或任意降低阈值掩盖真实压力。
