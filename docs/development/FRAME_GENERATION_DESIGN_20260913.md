# DLSSG 插帧完整管线设计与验证记录（2026-09-13）

状态：**完整目标设计，首轮原生接口验证完成；不是已完成的产品功能。**

后续实施、沙箱外关闭复测与多帧时间偏差见
[实施记录](FRAME_GENERATION_IMPLEMENTATION_20260913.md)。首轮关闭超时不能直接当作产品缺陷。

## 1. 交付边界：不以简化版替代完整功能

用户要求先验证，能做就完整接入，不能靠后续逐次补遗漏。设计与验收覆盖超分、增强、
插帧、HDR、预览、单项/批量导出、并行分段、缓存、取消/错误与分发。
可以按依赖顺序做实验，但不能把第一项实验成功当成完整交付。

- 目标为 DLSSG/MFG，不把 NvFRUC、RIFE、重复帧、混合帧作为自动替代后端。
- 不自动降分辨率、倍率、位深、光流质量、超分质量或关闭功能。
- 资源不足时允许减少**调度并发数**或等待，不能改变输出画质/时间线；仍不足则预检失败。
- 原厂/社区运行库是明确的兼容性配置，不静默换库；保存实际路径、版本、哈希与设备。
- API 成功、帧率标签升高、输出文件生成，都不等于生成帧有效或画质验收通过。
- 切镜、首帧、末尾与无有效历史不是正常帧对插值失败：按明确时间线规则保留真实画面，
  分别计数为 cut/endpoint hold，不把它们计为 generated。
- 正常连续帧对出现运行库失败/无效标记，严格导出停止并报告帧对；不悄悄补重复帧。

## 2. 主路径与超分顺序

主路径固定为：解码及时间戳 → 真实帧 RTX Video 超分 → 真实帧 DLSSNR 增强及强度混合
→ 最终画面坐标/颜色对齐 → DLSSG 生成中间帧 → 时间线合成 → 预览或编码/音轨封装。

1. 解码保留每张真实帧 PTS、duration、源 time_base、色彩描述及场景段标识。
2. 用户的超分关闭/2×/4×是宽高倍率。先解析最终尺寸，只对真实帧运行 VSR。
   1080p 的 2×为 3840×2160；1080p 的 4×为 7680×4320，不把超出插帧上限的 8K 隐式改回 4K。
3. 在超分后的真实帧上运行 DLSSNR，保留现有的增强风格/强度语义。
4. 将真实帧整理为最终要插值的画面：强度混合、用户明确要求的最终几何变换在此完成。
   若存在额外目标尺寸，统一由前端管线解析，禁止 FFmpeg writer 在插帧后再次偷偷缩放。
   VSR 只定义整数倍时，额外尺寸使用单独明确的 resize 步骤，不能冒充神经超分。
5. DLSSG 输入相邻真实增强帧的最终颜色与匹配的运动/深度/矩阵，输出同尺寸中间帧。
6. 原始真实帧和生成帧进入同一个有序时间线。生成帧**不回灌**到 VSR、DLSSNR 或真实帧光流历史。
7. UI 分界线、文字、播放控件等在插帧之后合成。烙在原片内的字幕属于输入画面，
   不能假定拥有独立 alpha；必须作为画质验收素材。

为什么这个顺序：以最终真实帧为生成端点，不让插值帧再次被增强模型重塑，避免额外时序
历史污染；超分和增强工作量按源帧数计算。与“先插帧再超分增强”相比，省去的是对生成帧
重复处理的工作，不是承诺处理速度直接乘倍率。GPU 同步、显存带宽、编码输出仍要增加。

不能把“原尺寸插帧后放大”作为性能降级捷径。完整质量路线的插帧在最终分辨率执行；
若对照实验显示顺序影响画质，应根据证据修订设计，而不是保留一条隐式低质量路径。

## 3. 超分倍率与插帧倍率独立

- 空间倍率 S：关闭、2×、4×；决定目标宽高与总像素数 S²。
- 时间倍率 M：关闭、2×、3×、4×为完整基础目标；6×仅在选定运行库和设备实测支持后声明。
- 30 fps、1920×1080，S=2、M=4 → 3840×2160、120 fps，原时长不变。
- 每对真实帧输出 M−1 个不同时间点的生成帧；不递归调用 2×去伪装原生 4×。
- 本地 SDK 的 multiFrameCount 是**新增帧数**，multiFrameIndex 从 1 起；不能把 M 直接当 count。
- 静态图片保留现有超分/增强流程，插帧不适用，不能覆盖保存的视频插帧偏好。

动态 MFG 是实时显示调度能力，不等同于固定 fps 视频导出。不能拿动态模式掩盖固定 3×/4×
不可用，也不能默认 DLSSG 支持任意 t（例如 24→60）。若提供指定目标 fps，必须由可验证的
时间采样能力实现；未经证明的非整数倍率组合在预检中明确拒绝，不通过丢/重复帧冒充插帧。

## 4. 分析输入不是一套数组随处传

需要区分两个消费者：DLSSNR 的时序引导、DLSSG 的运动/深度输入适配。

- NR 引导在 VSR 输出的相邻真实帧上分析，保持现有配置语义。
- FG 分析面向最终交付画面，其像素坐标必须与 FG 的颜色输入一致。
- 相同内容、帧对、分析尺寸、方向、模型、参数和几何条件下可以复用原始分析缓存；
  不因两个阶段都叫 motion vectors 就直接共享已变换的数组。
- 默认质量候选采用正确反向运动场与必要的双向一致性/遮挡验证；不把正向流取负数视为
  严格反向流。源图 resize 后，流场采样和位移尺度都要按实际宽高比例变换。
- NR 增强如果改变几何，增强前运动不能直接视为增强后精确运动；质量验证必须比较
  最终颜色重估与前置分析复用，只有通过后者才作为精确优化。
- 普通视频无真实引擎深度/矩阵。相对深度经过百分位归一化后不等于带物理尺度的深度。
  单位矩阵/平面深度仅可用于对应合成平面场景，不能直接成为正式默认配置。
- FG 用估计深度还是已验证的二维输入契约，必须由真实视频的遮挡/位移画质实验决定。
  如果无法达到标准，报告 DLSSG 视频适配未通过，不换算法或隐藏损伤。
- 用户关闭 NR 的可选光流，不应关闭 FG 必需输入；两者的设置、缓存和资源预算应分开。

缓存键至少包含源指纹、真实帧 PTS/帧对、seek/reset epoch、最终尺寸与有效区域、颜色契约、
VSR/NR 参数、分析模型/运行库哈希、方向/缩放。生成帧缓存还包含 M/index 与 FG 配置。

## 5. HDR 完整链路

现有 HDR 解码是归一化 PQ/HLG 编码值装进 RGBA16F，**不是线性 scRGB**。
现有 VSR 使用高位深路线，现有 writer 再编码为 10-bit。

新增 FG 必须显式声明色彩契约：像素格式、primaries、transfer、range、亮度参考、alpha。
颜色转换只在契约边界进行；“都是 float16”不能作为兼容证据。

- SDR、HDR10 PQ、HLG 分别做端到端测试，既测 FG 又测 S×M×NR 组合。
- 若 FG 要求其他 HDR 表示，正确转换再还原，不能用 SDR tone-map 结果作正式输入。
- 分析用 tone-map 副本可以供模型估计运动，但不能进入交付图像路径。
- 检查高光截断、暗部、饱和色、黑位、亮度漂移、NaN、量化和往返误差。
- float16 生成成功不等于 PQ/HLG 颜色正确；合成 >1 数值样本也不等于完整 HDR 视频验证。
- 继承本项目已声明的元数据边界：不新增“完整透传 Dolby Vision/HDR10+ 动态元数据”的承诺。

## 6. 一套核心，覆盖所有入口

正式集成新增不可变 ProcessingPlan（最终尺寸、颜色契约、时间线、设备、运行库、能力与预算）、
FramePacket（源身份/PTS/duration/scene/epoch/有效区/颜色/资源句柄）与 PairResult
（左右端点、生成时间点、有效性、generation_id/错误）。

GUI 只保存参数和消费结果。单项导出、批量队列、缓存预览、独立预览窗口与全屏复用同一
ProcessingPlan、PairProcessor 和时间调度器，不能在几个 gui.py 分支分别补插帧循环。

- 确保所有处理在明确的物理 GPU 上运行；CUDA 序号与 D3D LUID 映射不能靠名字猜测。
- VSR（现有 D3D11）、NR/FG（D3D12）间优先使用验证过的共享 GPU 纹理及 fence。
  不同运行库需要进程隔离时，以共享句柄与版本化 IPC 契约交换；不强迫混到同一进程。
- 不能把现有 CPU shared_memory 当作零拷贝。若某一互操作不可行，应实测精确回读/上传成本，
  如实说明性能边界；精确传输不是画质降级，但不能声称已实现全 GPU 管线。
- 外层任务异步，各个有状态模型内部按真实帧时序提交；有界帧池和背压，不缓存整片视频。
- 资源预算合计 VSR、NR、分析、FG、端点、生成帧、IPC、编码和预览，不分别“各自能放下”即可。
- 4K RGBA16F 单纹理约 63.3 MiB，8K 约 253.1 MiB；高倍率空间放大会放大全部在途资源。
- 隔离 worker 具备初始化、提交、flush、取消、关闭时限；超时终止本任务 worker，不杀其他进程。
- 对照显示先分别处理两侧真实/生成画面，再按同一 PTS 合成；不把带滑动分界的整张合成图
  直接送给 FG，否则分界线附近的运动会相互污染。

## 7. 时间线、切镜、末帧、分段

在 t_i、t_(i+1) 间生成 t_i+k*(t_(i+1)-t_i)/M，k=1..M−1。全部时间用有理数/整数 tick，
不能用累计浮点帧间隔维持长视频时间。

- CFR 使用真实有理帧率（例如 30000/1001），音轨保持原速与原起始偏移。
- VFR 根据各帧真实 PTS/duration 调度。仅读取平均 fps 再将 rawvideo 写为 CFR 不算 VFR 支持；
  必须新增能携带时间戳的解码/编码路径，并检验变帧率到目标时间线的映射。
- 以半开时间区间定义每段的所有权，任何边界帧/生成帧只有一个输出所有者。
- 首帧不外推；最后一张真实帧没有未来端点，按其真实 duration 显示至结束。
  CFR 为保持时长可能需要端点 hold；明确记录为 endpoint，不宣称是推理生成帧。
- 切镜处不融合两个无关镜头，保持切换 PTS；切镜前的时间槽保持该镜头真实端点，
  并重置 NR、分析与 FG 的历史，不伪造跨镜头运动。
- Seek、素材切换、尺寸/颜色变化、模型/参数切换均提升 epoch，废弃旧任务返回值。
- 并行分段需要左侧模型预热及右侧未来端点；预热长度由跨段输出对照决定，不能假定
  “每段加一帧”就覆盖 DLSSNR/FG 内部历史。按 owned interval 裁去预热与重叠部分。
- 若精确并行等价无法证明，调度保留有状态阶段的串行，其他无状态工作并行；这是保持正确性的
  调度策略，不改变倍率/分辨率/质量，不能把有接缝的分段输出交付。

## 8. 一次性验收清单

以下不是“下个小版本再补”，而是完整交付前的验收项：

1. 所选 NVIDIA/社区运行库、RTX 30/40/50 的实际设备矩阵；无实卡不标为实测支持。
2. FG 2×/3×/4×与可选 6×，每个中间位置的像素和有效性验证；拒绝仅看计数器。
3. S=1/2/4 与 M 的组合；最终分辨率上限、奇数尺寸、横屏/竖屏；不隐式降低质量。
4. SDR/PQ/HLG、高光暗部和字幕，NR 开关/强度、RAFT/NVOFA 配置的组合兼容性。
5. 真值合成运动、扣除中间帧的高帧率实拍对照、遮挡、面部、头发、快速横移、模糊、切镜。
6. 预览暂停/播放/拖动/逐帧、分界对比、缓存命中/失效、独立窗口、全屏、音画同步。
7. 单项和批量队列、保存恢复、重启、取消、写盘失败、OOM、worker 崩溃与超时退出。
8. CFR/VFR、非零音轨偏移、短片/单帧片段、末尾时长、分段拼接不重不漏。
9. 长视频显存/内存稳定；端到端吞吐区分真实帧/s、生成帧/s、成片 fps、处理倍率。
10. 插帧设置与运行库状态可诊断，正常失败不可伪成功；已存在功能回归全部通过。
11. 模型/运行库来源、许可证、可复现构建、更新器清单纳入维护流程。发版另行授权，
    遵守 editions、lite/full 增量和 check-upload，不在本验证任务自动发版。

## 9. 本次初始实测

环境：RTX 4070 SUPER、驱动 616.92；本地官方 nvngx_dlssg.dll 310.7.0.0。
源脚本 `scripts/dlssg_probe.cpp` / `.py`，构建 `scripts/build_dlssg_probe.bat`。
原生探针只复用既有 D3D12 工具函数，通过 public NGX API 调用 FG；不调用 NR，
不装调用方 hook、不修改 DLL、不加载游戏代理。父进程对每个案例限制 45 秒。

初始六案例（SDR/float16 × 2/3/4）：

- SDK 报 FrameGeneration.Available=1，MultiFrameCountMax=1（最多新增 1 帧，即 2×）。
- SDR 2×成功执行 8 次 Evaluate；合成平面横移的生成帧 MAE 0.001545716，
  相对前/后端点误差分别为 0.023994588 / 0.023159490。说明得到真正中间位置，非端点复制。
- float16 2×执行成功，但 >1 高光输入 MAE 0.572680067，远高于允许误差；
  不得因“比前后端点略近”便宣称 HDR 通过，需核对颜色契约。
- SDR/float16 的 3×/4×均 Evaluate 返回 0xBAD00005；运行库明确记录
  `Multi frame is not supported on this device`。不是我们的导出设置把倍率关了。
- 两个 2×案例已完成 release/destroy parameters，但卡在 Shutdown1，45 秒由父进程终止；
  不能把像素成功记为生命周期通过，也不能仅凭日志推断是遥测/网络导致。

第二轮增加 OutputDisableInterpolation GPU 回读、绝对误差阈值与显式 shutdown 阶段标记。
初始轮未读取有效性标记，因此只是像素接口证据，不是最终验收。

补测结果：

- SDR 2×：frame 0 的 disable=1；frame 1..7 均 disable=0，像素误差不变，绝对误差检查通过。
- >1 float16：有效性标记相同，但输出峰值恰为 1.0、MAE 0.572680067，像素检查失败。
  只能确认该输入契约下出现裁切，不能泛化成“DLSSG 不支持 HDR”。
- 归一化 float16（`hdr-coded`，0..1、colorBuffersHDR=true）：MAE 0.001548287，
  相对前/后端点为 0.024001149 / 0.023136296；有效性及像素检查通过。
  这是归一化编码值域的合成运动，不是实际 PQ/HLG 内容或元数据验证。
- 所有新增 2×案例均在 `shutdown_begin` 后超时，关闭问题可重复。
- 最终探针修正：MultiFrameCountMax 是输出能力，只读，不写入作为请求。
  以正确只读能力契约重跑 SDR/归一化 float16 的 3×/4×，仍拒绝多帧请求。
- 整个验证没有使用第三方游戏代理、修改 DLL 或切换算法，也没有降低倍率重试。

固定输入 DLL SHA256：`135eaf0733c1e37381a8c28abcf7a862404a54132b81787c04e35d09efc5e36f`。
补测命令增加 `--label validity --multipliers 2`、
`--label coded --multipliers 2 --formats hdr-coded` 或
`--label capability --multipliers 3 4 --formats sdr hdr-coded`。

结论：**无需游戏交换链即可执行官方 2× DLSSG 的离线计算已获得实测证据；完整视频功能
尚未通过。** 多帧兼容性、HDR 色彩、真实视频分析输入和关闭行为均为不可略过的门槛。
