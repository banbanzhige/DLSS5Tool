# 原生优化拆分与重复渲染诊断（2026-09-12）

## 结论

本轮只做诊断，不修改产品逻辑、不部署DLL、不打包。此前“兼容提交完全一致”的结论需要收窄：
它在大多数控制中一致，但组合候选的强制等待诊断版也曾在兼容单帧中出现偏差。
目前不能把异常全部归因于合并提交、深度优化、队列扩展、CPU/GPU重叠或“随机种子”。

能够确认的是：

- 不增加到16槽，仅深度清理也能复现偏差；队列深度不是必要条件。
- 不包含深度清理，仅队列扩展也能复现偏差；深度清理不是必要条件。
- 合并单帧以及兼容单帧均出现过偏差；多帧同时在途不是必要条件。
- 原DLL和重新编译旧源码的首段控制全部一致，但有限重复不能证明永远确定。
- 不同构建和相同构建的多数运行相同、少数不同；仅一次A/B成功不足以验收。

保持现有运行环境和兼容默认，暂不升级实验候选。单通道内存/传输优化的收益方向仍成立，
但“不改效果”的原生验收不能凭此前短测直接下结论。

## 构建隔离方式

`scripts/native_isolation_probe.py`从Git HEAD读取基线C++，从当前工作树中提取队列改动，
以匹配次数必须为1的断言拆出候选。诊断单测确认深度版不含队列预算/接口，队列版不含UsesDepth/能力位8。
没有手工修改产品源文件，也没有多个可执行候选并存：`build/candidate.dll`在所有子进程退出后逐次重建。
原`runtime/dlssnr_host_v2.dll`始终只读，作为回滚基线。

| 版本 | 内容 |
| --- | --- |
| runtime | 用户当前运行的旧DLL |
| baseline | HEAD原生源码，当前编译器重新编译 |
| depth | 仅深度清理，槽位上限仍为3，不含预算接口 |
| queue | 仅1–16槽位、资源预算及实际槽数接口，不含深度清理 |
| wait | 深度+队列组合，仅把异步提交的wait=false改true，用于诊断，不用于交付 |

## 首段96帧结果

原片《260429广寒宫98s.mp4》，1080×1920，前96连续帧；每次独立进程，固定所有效果参数。

使用同一源码Python包装器和worker，不复制CUDA环境，光流缓存关闭。
每轮兼容/合并依次运行，奇数轮顺序反转；GPU试验不并行，没有终止用户其他程序。
正确性按完整RGBA帧SHA256，另记录全帧RGB均值，不使用有损编码或只看缩略图。

## 解释边界与后续方向

此次不是对NGX内部实现的证明。未发现/设置随机种子接口，未开启GPU验证层或抓取NGX内部执行轨迹。
编译布局、分配和提交时机、运行时内部状态、驱动调度仍是待验证因素，不把猜测写成根因。
wait诊断只改EnqueueFrame的等待；它的兼容路径与组合候选相同，异常不能归咎于这个等待改动。
首段未对每次解码输入单独存哈希，第二段增加了输入哈希验证。
本轮没有逐帧保存/复用RAFT原始运动向量哈希，因此真实光流异常仍可能包含模型/传输变化，
不能单凭解码输入相同就断定一定是原生DLL。零引导异常不经过RAFT，说明至少还有独立于光流模型的因素。

前一轮已经证明“分段重置历史”会产生持续差异，该结论与此次“同起点偶发不一致”是两类问题，
不应相互替代。当前仍不推广多进程分段拼接，也不全局改用合并提交。

下一步若要继续定位，先固定并记录每帧原生输入、reset序列和输出，在独立诊断构建中开GPU验证/抓取，
检查提交资源及NGX状态；有具体证据后才改实现。不能靠随机换种子、增加队列或强行等待作为“已修复”。
