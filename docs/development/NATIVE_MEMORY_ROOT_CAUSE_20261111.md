# 原生内存增长根因复核：NVIDIA 621.14 · 2026-11-11

## 本轮结论

用户明确优先追查原生内存增长，中途续导搁置。本轮没有实施续导或修改产品处理路径。

**已在当前 621.14 驱动独立复现每线程约 184 bytes 的原生堆保留，且组合负载中的分配栈、
线程数量和堆增量相互对应。** 这补上了之前“621.14 仍增长，但未重抓分配栈”的缺口。

当前主要机制是：CUDA 初始化触发 `NvMessageBus.dll` 大量创建短线程；当同一进程也驻留
`nvwgf2umx.dll` 时，后者在线程初始化路径保留小块堆分配。线程正常退出后，这些块仍累积。
尚未完成的是短线程风暴的触发责任隔离，以及原用户和全部产品处理路径的最终回验。

**确认了当前驱动的一处缺陷及本机主要增长机制，不等于已经修复 P0。**
已有工作进程回收和压力恢复继续作为保护，不能替代根因修复或长稳验收。

## 环境与实验范围

- RTX 4070 SUPER、64 GiB RAM、Python 3.13.3，复用现有只读 `.venv` 依赖及运行库。
- 本机驱动文件版本 `32.0.16.2114`，描述 NVIDIA D3D10 Driver, Version 621.14。
- `nvwgf2umx.dll` SHA256：`1151c9d103cb9b3149998a5038a1270274fa43506154eff46ed7b86a057e87c1`。
  实际路径和相关模块身份见证据中的 `installed-module-metadata.json`。
- 四组最小对照各空闲 60 秒；另做组合负载分配栈追踪，以及原生空线程程序的有／无追踪对照。
  全部关闭主动 GPU 查询，没有 `nvidia-smi`／PDH 轮询；没有初始化 NR 或加载项目处理 DLL。
- 最小对照沿用已登记的诊断脚本。外部观察按 PID＋创建时间归属，线程计数 DLL 仅加载在诊断自身，
  无远程注入。堆追踪仅临时修改诊断自身已加载模块的 IAT 引用，不改驱动文件或机器配置。

本轮未安装／卸载驱动或应用、改覆盖层／注册表／服务设置，没有运行全仓库回归。

## 1. 两个条件叠加，出现大幅增长

下表为每组首尾诊断检查点的默认原生堆已分配量变化和线程创建增量。
每组仅一次约 60 秒窗口，不作为五分钟或半小时平台验收。

| 最小负载 | 原生堆增量 | `NvMessageBus` 短线程增量 | 模块观察 |
| --- | ---: | ---: | --- |
| 仅 CUDA 初始化 | +0.255 MiB | 475,928 | 有 MessageBus；未观察到 `nvwgf2umx.dll` |
| 仅 D3D11＋一次空计算 | +0.200 MiB | 0 | 有 `nvwgf2umx.dll`；未观察到 MessageBus |
| CUDA＋D3D11＋一次空计算 | **+70.390 MiB** | **401,100** | 两者均驻留 |
| CUDA＋D3D12 设备创建 | **+70.586 MiB** | **401,575** | 两者均驻留 |

按同一工作进程的外部私有提交、排除最初十秒后分窗比较，后两组分别约
77.06、76.94 MiB／分钟；前两组约 3.55、3.45 MiB／分钟。
Python 元数据扫描和记录会增加小幅观测开销，不能将前两组称为已通过平台。
默认原生堆与整个进程私有提交是不同指标，不能混用。

MessageBus 入口均位于实际加载模块范围内的 `+0x251510`。未用最近导出符号推测私有函数名称。
模块不存在的观察只覆盖相应快照，不证明该 API 在其他条件下永远不会加载该模块。

组合 D3D11 的数量核对：

```text
401,100 × 184 bytes = 73,802,400 bytes ≈ 70.383 MiB
独立 HeapSummary 增量 = 73,809,344 bytes ≈ 70.390 MiB
差值 = 6,944 bytes
```

线程计数与堆查询不是原子快照，不能从这组接近的数值推导所有小额分配的精确来源。
结合下一节的独立复现，它强力支持按线程保留是该组合负载的主要原生堆增量来源。

## 2. 当前驱动独立复现：无需 CUDA、D3D 或 NR 调用

新增 `scripts/native_driver_thread_probe.cpp`：只加载指定的已安装 DLL，串行创建、等待并关闭
30,000 个空线程。线程自然返回，不用 `TerminateThread`；任一时刻最多一个额外测试线程。
程序不调用 CUDA、NGX 或 D3D API。

用同一个可执行文件分别加载 `version.dll` 与当前实际使用的 `nvwgf2umx.dll`；
有追踪和无追踪分别在新进程中运行，由父进程 Job 及启动 gate 限定所有权。

| 条件 | 10,000 → 30,000 线程的默认堆变化 | 平均新增量 |
| --- | ---: | ---: |
| 系统 DLL，无追踪 | 0 bytes | 0 bytes／线程 |
| NVIDIA 驱动，无追踪 | **3,680,000 bytes** | **184 bytes／线程** |
| 系统 DLL，有追踪 | 0 bytes | 0 bytes／线程 |
| NVIDIA 驱动，有追踪 | 约 3.68 MB，含少量诊断分配 | 约 184 bytes／线程 |

驱动追踪的主要一条栈精确记录 **30,000 笔 × 184 bytes = 5,520,000 bytes**，观测释放为零；
无对象表或栈表丢失。独立的无追踪 HeapSummary 对照避免仅凭 IAT 配对统计下结论。
这仍是有限线程窗口，不是所有驱动内存和释放路径的完整审计。

在裸线程程序与组合负载中，均抓到当前驱动相同的模块相对栈：

```text
nvwgf2umx.dll + 0xfe6b6c
nvwgf2umx.dll + 0xfb46e5
nvwgf2umx.dll + 0xfb499b
nvwgf2umx.dll + 0xfb4df2
nvwgf2umx.dll + 0x1d2802
ntdll.dll ...
```

没有 NVIDIA 私有符号，不为这些偏移指定未经核实的内部函数名。
该机制与外部 MIT 最小复现报告一致，但本轮结论有当前机器和当前版本的独立证据：
[ArtistDeveloper 的复现](https://github.com/ArtistDeveloper/nvwgf2umx-thread-leak)
／[NVIDIA 缺陷 6672628 原报告](https://forums.developer.nvidia.com/t/nvwgf2umx-dll-leaks-184-bytes-per-thread-in-its-dll-thread-attach-handler-595-95-580-88/381379)。

## 3. 追踪与失败记录的边界

- 计数器自检为 50 次线程创建／50 次退出，无未分类入口。
- 堆追踪自检准确记录 16 MiB 分配、24 MiB 重分配和释放后归零，69／69 个引用恢复。
- 四组矩阵、组合堆追踪和四组配对裸线程用例均完成处理／退出检查，相关源码／运行库清单
  在各自测量期间不变，未触发安全停止或监督器兜底清理；不能因此标平台通过。
- 组合 Python 堆追踪使线程创建显著减慢，并达到 8,192 栈容量，最终丢弃约 127 万条新栈记录。
  已有驱动栈持续记录到 97,310 笔 184-byte 保留。该轮仅用于确认路径，不能用于完整来源占比或性能比较。
- 独立裸线程有追踪配对没有上述容量丢失，引用恢复与自然进程退出均完成；无追踪对照进一步复现。
- 最初构建命令因工作目录尚未创建而未启动，没有执行构建／测试。
  既有汇总工具首次遇到混合结果结构报 KeyError；后续按各结构分别调用解析函数，无效汇总未用于结论。

### 现有 CUDA VSR 路径的探索仍为失败

额外用现有已验证 CUDA VSR 组件、最高质量、320×180 → 640×360 SDR 实际处理三帧，
首帧后空闲约 60 秒。该轮模块快照没有 `nvwgf2umx.dll`，MessageBus 短线程仍存在。
该窗口默认堆仅增约 0.377 MiB，提供了“部分路径可能避免两条件同进程叠加”的线索。

但直接调用 `CudaVSR.close()` 没有在整体 120 秒诊断期限内完成，监督器关闭本次专属 Job；
**整轮结果为失败**，不能称已经解决增长／关闭问题，也不默认修改产品后端。
Job 清理后的退出码虽为零，仍按超时／需要回收记录失败，不将它作为正常退出。
此时没有抓取阻塞线程栈，不能仅凭调用位置认定卡在 NGX Shutdown。
需按真实生产工作进程的退休方式另行验证，并补长稳和质量对照，才可评估为兼容路径。

## 建议的下一步

1. **优先查 MessageBus 短线程风暴的触发条件。** 保持相同驱动、GPU 和负载，核对相关 NVIDIA
   可选组件／诊断或覆盖层路径的真实模块身份，做可恢复的单变量环境对照。观察到 `nvdiagclt64.dll`
   不等于已经证明它就是控制者。旧浮窗开关和服务重启均未形成有效缺席对照，不重复当作根治。
2. **携带当前版本复现推动驱动侧修复。** 裸线程程序无需模型和本项目，已有当前驱动 SHA256、
   系统 DLL 对照、无追踪堆计数和追踪栈，可作为供应商复现材料。本轮没有向外发送消息或提交 issue。
3. **应用侧按实际模块和调用合同评估绕开条件。** 保留已完成的显卡查询隔离，排查不必要的
   CUDA／D3D 同进程初始化；对必须同时使用两者的 NR／SDK 路径，不能仅靠改 Python 线程池修复
   NVIDIA 内部创建的线程。现有 CUDA VSR 探索先解决上述退休验收，再做连续处理验证。
4. **继续保留进程生命周期与内存余量保护。** 它能限制故障影响，但仍需同一工作进程五分钟空闲、
   至少三十分钟连续处理、重复任务基线和原用户负载复验，沿用原 P0 门槛。

不直接释放未知驱动内存，不改驱动指令或强行关闭其线程通知，不用降低预留或清工作集冒充修复。
环境变更须先明确具体组件、回滚和影响，本轮没有静默修改机器配置。
