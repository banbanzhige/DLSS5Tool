# 多帧队列、光流优化与光影一致性综合验证

日期：2026-09-12。结论：**保持兼容提交默认；不部署本次候选DLL。**
1–16帧已实现为源码实验选项，但重复渲染一致性尚未通过，不能作为正式性能承诺。

## 关键结论

1. 用户担心的分段光影不一致有实测依据。在兼容单帧下，从第20帧新建会话，
   或同会话在第20帧reset，结果逐像素相同；但都不同于从第0帧连续渲染。
   因此时序历史重置足以解释差异，无需假设每次都抽取不同随机种子。
2. 候选宿主的合并双帧、八帧各一次重复运行发生像素偏差，其他多数重复一致。
   旧DLL的额外四轮合并双帧全部一致。尚不能确定是NGX运行时非确定性、调度，还是候选变更回归。
   不宣称合并提交无损；新候选不进入runtime，不全局切换默认。
3. 在此4070 SUPER和原片上，零引导2/4/8/16帧纯处理均约140fps，超过2帧没有稳定额外收益。
   开放上限是给其他硬件/负载的实验空间，不是“显存占满就会更快”。
4. 不改兼容提交时，紧凑光流传输有小幅收益，原始预测缓存命中有明显调参收益；
   NVOFA更快但输出不同，只能是有画质取舍的显式选项。

## 范围与方法

- 同一《260429广寒宫98s.mp4》，1080×1920，前40个真实连续帧。不是整片/多素材验收。
- GPU RTX4070 SUPER 12GB，驱动616.92；不杀用户进程、不独占GPU。
- 所有原生对照使用同一内置NGX运行时。真实光流复用`tmp/guidance-cuda-env`运行源码worker，
  RAFT-Large FP32、6次更新、分析长边512（实际288×512），不加载深度模型。
- 固定style=0、强度/色调/结构/皮肤=1、auto-mask开启；无缩放、无超分、无HDR。
- 两轮反向顺序，每个配置独立进程；另外增加4轮兼容/合并2/合并8以及4轮旧DLL控制。
- 正确性阶段：原尺寸RGBA8逐帧SHA256、相对连续渲染的RGB MAE、最大通道差、变化通道比例、
  平均RGB偏移；保存首尾对照PNG，不从有损视频估计误差。
- 速度阶段独立：先再预热16帧，零引导计时160帧、光流计时48帧，循环使用这40帧。
  不含解码、编码、GUI、哈希、像素比较或首次加载，因此表中是process吞吐，**不是导出fps**。
  循环边界不是连续自然运动，不能用这段速度阶段替代时序画质验收。
- 全局缓存关闭，只有明确标注warm_cache的测试打开512MiB缓存。保留前40帧完整历史的正确性基线。
- 没有测后台解码改造、CUDA/D3D12零拷贝、整片编码与预览8.7fps时间线；这些不在本轮已验证收益中。

## 不依赖合并提交的优化

均为新候选、兼容单帧；除了列出的变量，其他设置一致。

| 方案 | 两轮process fps | 编码前结果 | 判断 |
| --- | --- | --- | --- |
| RAFT，完整full_v1传输 | 18.41 / 19.75 | 与RAFT基线一致 | 对照 |
| RAFT，仅光流紧凑传输 | 20.41 / 20.27 | 与RAFT基线一致 | 小幅收益，优先保留 |
| RAFT，512MiB原始光流缓存命中 | 26.47 / 28.95 | 与RAFT基线一致 | 调参/重看收益，不是首次导出加速 |
| NVOFA 1×1，仅光流紧凑传输 | 29.99 / 29.81 | 与RAFT不同 | 显式性能选项，不当作等价替代 |

紧凑传输相对完整传输两轮均值约+6.6%，单轮收益约2.6%～10.9%，说明负载噪声不可忽略。
使用旧DLL/full_v1与新DLL/紧凑传输的组合对照则为19.02/19.37 vs19.01/20.67fps，
第一轮几乎无收益；不能宣传固定百分比或把局部内存减少当整链路提速。

真实协商确认：full_v1/shared_memory_v1与flow_only_v2/shared_memory_flow_v2。
1080×1920共享映射由约31.64MiB降至23.73MiB（-25%）；不代表总进程/总显存-25%。
所有光流记录depth_model_calls=0。深度模型此前已经不运行，本优化减少的是剩余数据通道开销。

缓存额外确认：28.86fps、cache_flow_hit=true、flow_model_calls=0、depth_model_calls=0，
40条缓存约45MiB，无驱逐；不是跳帧或复用最终DLSS输出。首次处理没有这项收益。

NVOFA相对RAFT紧凑版平均约+47%，但最差单帧RGB MAE约0.993/255、最大单通道差54。
这些差异不等于画质下降程度；未做连续播放盲测，不判断哪个观感更好。

### 重复一致性异常

- 零引导new_merged8-r1：40帧中34帧不同，首次差异第6帧；最差帧MAE0.548、最大通道差16。
- 零引导repeat-merged2-1：最早第24帧不同；最差帧MAE0.512、最大通道差14。
- 候选兼容的6次运行全部一致；候选合并2/8各6次中各有1次不同。
- 旧宿主兼容初始2次+额外4次均一致，旧宿主合并2额外4次均一致。
- RAFT光流两轮各配置在这个40帧窗口全部与基线一致，但不能因此抵消零引导异常。

异常不只发生在新增>3队列，因此不能简单说“8帧太深”；同样，旧DLL四次通过也不能证明旧路径永远确定。
需要将候选深度清理和队列扩展拆成受控构建，固定输入继续交替复测，才能归因。
本轮遵守一个候选原则，没有为强行归因复制多套运行库/环境。

## 时序历史与分段拼接

对前40帧连续结果，将第20～39帧分别按以下方式处理。以下均为兼容单帧，不依赖合并提交。

| 模式 | 零引导第20帧MAE | 真实光流最差帧MAE | 结论 |
| --- | ---: | ---: | --- |
| 从第20帧开新进程/会话 | 2.418 | 2.379 | 明显偏离连续历史 |
| 从第12帧开始，丢弃8帧预热 | 0.954 | 0.999 | 缩小但没有消除偏差 |
| 从头同进程运行，第20帧reset | 2.418 | 2.379 | 与新会话段结果逐像素相同 |

零引导直接分段第39帧仍有MAE0.903，8帧预热后第39帧仍有0.738。
因此默认8帧预热不等于无缝保证；不能将分段问题用更深队列解决。
当前`parallel_export_worker.py`确实为各段建立独立会话，在process_start reset并丢弃warmup帧。
本次模拟的是该历史边界，不是完整多进程编码拼接复现。

“合并提交”合并的是一次GPU命令提交中的上传/计算/回读，仍是一个按顺序维护历史的DLSS会话；
“并行分段导出”才是多个独立DLSS会话后拼接文件。用户描述可能同时涉及二者，需要分开定位。
没有找到或修改所谓随机种子接口，也没有证据支持“每次都换种子”的确定结论。

## 已实现的实验入口与安全边界

- Python/UI/设置/资源估算统一1–16帧，默认仍为兼容提交，未强制改成合并或16帧。
- 新DLL导出`dlssnr_queue_capacity`，报告实际分配槽位；旧DLL没有该接口时最多请求/报告3帧。
- 新宿主按所选DXGI设备的进程显存预算和系统可用内存限制队列；预算未知回到旧上限3，
  小尺寸高显存可以选择16，超大图/同步路径仍为1。失败仍明确报错，不改画质、不偷偷切GPU。
- GPU保留NGX/引导余量，RAM估计考虑上传/回读及调用者帧；这是启发式边界，不是OOM绝对保证，
  不会在每帧查询预算，也没有验证所有显卡/4K HDR/多进程组合。
- 队列控件显示请求/实际帧数及实验一致性警告；受UI/UX技能指导，说明文字常驻而非仅悬浮提示。
- 帧序、槽位独占、fence等待机制未改；没有让同一个RAFT模型多线程并发调用。

Windows显存预算可能变化，超预算会换页/卡顿，不能用占满显存判断优化成功：
[Microsoft QueryVideoMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo)。

验证：候选DLL构建成功；C++资源上限测试通过；两组Python回归143+106项通过，
最终资源估算/真实Tk队列控件27项复测通过（各组存在重叠，不合计为独立测试数）。
`git diff --check`通过，仅已有CRLF规范提示。未覆盖当前runtime、mods、用户设置或发布包。

## 综合建议

1. 保持兼容单会话，优先紧凑光流通道；先拆分排查候选多帧异常再部署任何新原生DLL。
2. 保留原始光流缓存，强调只改善已算过帧的调参和重看，不能对首次导出承诺28fps。
3. NVOFA作为可选速度档，要求真实运动片段盲测后选择；不替换RAFT默认。
4. 不默认推广合并多帧或分段并行导出；16帧仅为实验入口，当前机器没有明显额外收益。
5. 正式验收需增加长片、多素材、切镜、肤色/暗场、HDR、内存压力和分段边界；
   预览解码线程优化另做分阶段时间线诊断，不能用本轮数据宣称已解决8.7fps。
