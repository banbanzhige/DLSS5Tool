## 已实现的代码

- `dlss5tool/frame_timeline.py`：不可变 ProcessingPlan/ColorContract/SourceFrame，
  独立空间/时间倍率、最终尺寸解析、明确的阶段顺序、质量验证能力门控。
- 同模块的精确有理数 CFR/VFR 时间线，真实/生成/切镜保持/末帧保持的明确分类；
  切镜不生成混合镜头，首尾时长不靠改 FPS 伪装。
- 分段采用半开时间所有权；缺少右侧未来端点、跨 epoch、缺帧、时间间隙或重叠均报错；
  非末段不允许将缺少的未来帧伪装成末帧保持。边界不能切在输出帧 duration 内。
- 帧组提交前检查数量、子帧顺序、时间戳、有效性和 epoch；不接受正常帧对失败后补重复帧。
- `scripts/dlssg_ada_gate.h`：只针对实测 4070 SUPER 与精确 SHA256 的 310.7 运行库，
  研究性解锁限定单进程；保留原倍率/索引校验，不修改磁盘文件或系统驱动设置。
- `scripts/rtxmfg_temporal/`：固定提交的 MIT 基线时间内核修正与来源/许可证。
  不是上游完整发布构建：未包含默认开启的 mask-only 优化，也未包含实验性 pull/scatter。
  不捆绑提取模型/内核数据，不宣称与完整上游等效。
- 可选的研究预设 B 调用点适配只在 NGX 初始化前对精确匹配的本进程代码生效；
  不写全局 NVIDIA DRS，不影响其他进程，错误退出而不继续不明状态。
- 原生探针增加组级有效性、BackbufferFrameID、双端点纹理轮换、各子帧独立输出纹理，
  一组只上传一次输入，以及独立的时间位置拟合检查。
- Python 探针将像素、时间位置、关闭结果分列；任一必需项失败返回非零，
  不再因父脚本顺利跑完就返回成功。

时间线模块尚未连接 GUI/播放器/FFmpeg。它支持 VFR 时间描述，**不代表已有解码器/编码器
已支持新的 VFR 插帧路径**。没有可执行的生产 FrameGenerationSession，也未修改用户设置。

## 多帧验证结果

环境：RTX 4070 SUPER，驱动 616.92，本地官方 DLSSG 310.7.0.0。
运行库 SHA256：`135eaf0733c1e37381a8c28abcf7a862404a54132b81787c04e35d09efc5e36f`。
场景：1920×1080 平面纹理匀速平移，每源帧 8 像素，精确运动向量、深度与静止正交相机。
时间位置拟合独立于请求 index，以 0.01 源帧间隔搜索最佳位置。
这是一个诊断样本，不是多种真实素材上的通用质量排名。

| 模式 | 请求位置 | 拟合位置 | 时间误差检查 |
| --- | --- | --- | --- |
| 2× | 0.50 | 0.50 | 通过 |
| 3× | 0.333 / 0.667 | 0.46 / 0.69 | 首个生成帧失败 |
| 4× | 0.25 / 0.50 / 0.75 | 0.40 / 0.50 / 0.71 | 首个生成帧失败 |

SDR 与归一化 float16 在这一案例中得到相同拟合位置。阈值为 0.05 个源帧间隔；
3×/4×的首个生成帧分别偏离约 0.127/0.15，不能通过放宽阈值隐藏。
最后 `ring` 轮中 2×两种格式通过，3×/4×两种格式全部因时间位置检查失败退出；父脚本返回 1。

已尝试并记录：

1. 仅解锁原厂倍率分支：Evaluate 可以执行，但不足以认证完整 MFG。
2. 上游基线 temporal 修正：源资源/PTX/输出哈希与布局检查通过，但上述偏差仍在。
3. 按帧组保留 OutputDisableInterpolation：第一子帧更新组状态，其他子帧复用组状态。
   此前每个子帧重新填 sentinel 的探针方式会把后续未重写误记为无效；已修正。
4. 明确 BackbufferFrameID：未消除偏差。
5. 初始化前设置研究预设 B：调用点匹配成功，未消除偏差；不将此等同于模型内部选用已被单独证明。
6. 轮换两个输入纹理、给每个子帧独立输出、每组只上传一次：未消除偏差。

目前不能确定偏差来自普通视频式合成输入契约、剩余模型路径、样本本身的估计误差，
或与完整上游接入的差异。不能泛化成“RTX 40 绝对不能多帧”，也不能声称已修复。

## 关闭问题的修正结论

同一官方 2×探针在沙箱外运行，约 4.415 秒完成初始化、8 次 Evaluate、像素与时间验证、
ReleaseFeature、DestroyParameters 和 Shutdown1（返回 Success），进程返回 0。

因此先前的 45 秒关闭超时与执行环境有关，不能直接断言产品运行库有关闭缺陷。
仅一次沙箱外成功也不代表长期关闭稳定性已验收。保留 worker 超时边界设计。
`--shutdown process` 只是隔离诊断方式，不是 NGX 正常关闭通过，也没有接入产品作为隐藏处理。
