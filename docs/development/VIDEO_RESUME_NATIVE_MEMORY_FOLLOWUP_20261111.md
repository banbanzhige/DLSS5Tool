# 视频中途续导与原生内存增长：源码核查及建议 · 2026-11-11

## 结论

**中途续导有实际代码可参考；尚未找到已证明匹配本项目空闲私有提交增长的公开根治补丁。**
建议补充可恢复的视频片段事务，并按实际内存压力回收原生工作进程；另用分配栈和有效的环境对照追查根因。
这可以减少长视频失败后的重复处理，但不能提前宣布原生增长 P0 通过。

当前 `cfd6022` 已补齐内存压力后的回收、等待、重建和有限队列重试，**视频仍从整项开头重做**。
本报告提出的新增能力是保存片段和精确续接位置，不是重复实现已有队列恢复。
已有行为和验收见 [队列恢复报告](QUEUE_MEMORY_RECOVERY_20261111.md)。

本轮为公开源码、发布说明与本地证据核查；没有运行外部最新版、替换 DLL、安装驱动或修改系统设置。

## 已核实的外部实现

### Veyra：故障后换进程，保留有效输出继续

核对最新正式版 v2.1.5（2026-11-10）及源码 `d57ac320ca9b542226dc94fc0d6e49e3d97dd96c`，GPL-3.0。

- 父进程识别工作进程退出码 4：显卡重置后，工作进程已关闭一个有效片段并报告续接位置。
- 父进程保留片段及其源时间起点，清理旧进程，用新进程继续相同任务；续接位置必须向前推进。
- `kMaxExportParts=4`，故障续接有上限；不能继续时报告并保留已有片段。成功后由最终工作进程拼接。
- 合并前检查轨道及视频编码参数；按各片段源时间起点修正 packet 时间戳，对不前进的重叠 DTS 做去重。

[父进程实现](https://github.com/Likely7/Veyra-NRVideo/blob/d57ac320ca9b542226dc94fc0d6e49e3d97dd96c/src/engine/ExportJobManager.cpp#L199)
／[故障片段收尾](https://github.com/Likely7/Veyra-NRVideo/blob/d57ac320ca9b542226dc94fc0d6e49e3d97dd96c/src/engine/VideoExportJob.cpp#L365)
／[片段合并](https://github.com/Likely7/Veyra-NRVideo/blob/d57ac320ca9b542226dc94fc0d6e49e3d97dd96c/src/engine/VideoExportJob.cpp#L457)

边界：这是设备故障恢复，未确认主动 RAM 压力轮换，也未确认整个应用重启后的持久恢复。
其续接公式使用“片段末尾减半个输出帧间隔”，不直接移植到本项目的 VFR 时间线。
所查导出处理在首帧重置图内历史，不能以能够拼接替代时域质量验收。

### Visual Enhancer v15：分块、检查点、历史输入重放、暂停释放进程

历史版本 v15.0 固定提交 `04d97b05b822abce26196a412b08a2183ed2278a`，2026-10-08。
本次已核对最新发布为 v22.0（2026-11-04），但这里描述的是 **v15 标签的实际实现**，不把旧架构自动归给新版本。

`rolling_passes.py` 的路径可以确认：

1. 每个 part 的各处理阶段通过独立工作进程执行，阶段结束后卸载；缓存有预算及所有权记账。
2. 片段加入 delivery 后更新 `checkpoint.json`，记录下一段起点、已拥有的源帧序号及解码游标。
3. 暂停会终止并回收工作进程，丢弃未提交 part 的缓冲；恢复后从上一检查点重做该 part。
4. 源游标保留前面的历史范围，恢复解码从此前位置开始；缓存另保留最多 32 帧上下文。
   预热帧与本段拥有的输出由源帧序号或精确时间区间区分，避免重复交付。

[分块提交与暂停恢复](https://github.com/Merserk/dlss5-visual-enhancer/blob/04d97b05b822abce26196a412b08a2183ed2278a/src/desktop/rolling_passes.py#L235)

／[解码恢复](https://github.com/Merserk/dlss5-visual-enhancer/blob/04d97b05b822abce26196a412b08a2183ed2278a/src/desktop/rolling_workflow.py#L270)

## 原生增长：目前最强的解释及剩余缺口

不是完全没有定位：

- 2026-10-20、驱动 617.42 的本机分配追踪中，同一 `nvwgf2umx.dll` 栈的请求均为 184 bytes；
  合成器一轮末尾观测到约 39.83 MiB 未配对释放，占该轮观测净保留约 99.16%，独立 HeapSummary 增量约 40.08 MiB。
  探针存在覆盖边界，不能把配对统计当作完整泄漏审计。
- 同机另轮最小 CUDA＋D3D11 负载 60 秒出现约 33.5 万个短线程，入口主要在 `NvMessageBus.dll`；
  服务重启后仍约 21.3 万个。原版 Veyra 的外部 ETW 也记录到同一入口的大量短线程。
- 外部 MIT 项目 `ArtistDeveloper/nvwgf2umx-thread-leak` 有独立最小复现：加载该驱动后创建／正常退出线程，
  驱动在线程通知中保留 184-byte 分配；对照加载系统 DLL 时稳定。

因此“**异常短线程创建叠加驱动按线程保留分配**”是目前较强的机制解释。
但 `NvMessageBus` 为什么在本机触发大量短线程、哪些可选组件／环境参与，尚未完成有效因果隔离。

[本机原生分配证据](P0_NATIVE_ALLOCATION_20261020.md)
／[本机短线程与服务重启结果](P0_COMPLETION_20261020.md)
／[原版参考项目对照](P0_UPSTREAM_COMPARISON_20261020.md)
／[外部最小复现](https://github.com/ArtistDeveloper/nvwgf2umx-thread-leak/blob/533aff215d351c02f2bf908c5abb041b048b2f29/README.md)

截至本轮核查，公开 NVIDIA 缺陷 6672628 的论坛记录没有可核实的官方结案／修复驱动版本。
该外部复现测试的是 595.95、580.88，不能直接替代本机 621.14 的新分配栈。
[NVIDIA 开发者论坛原报告](https://forums.developer.nvidia.com/t/nvwgf2umx-dll-leaks-184-bytes-per-thread-in-its-dll-thread-attach-handler-595-95-580-88/381379)

2026-11-11 的本机 621.14 对照仍然增长：无项目处理 DLL 的 CUDA＋D3D11 空闲约 74.7 MiB／分钟，
NR／VSR 空闲约 61.0／63.1 MiB／分钟；后续没有主动 GPU 查询的短测也复现增长。
尚未为 621.14 重抓分配栈，不能宣称其全部增量已归到旧版的 184-byte 路径。
空闲测量期间更新器数为零，更新器生命周期修复不是这部分增长的充分解。

## 建议落地方案

### 第一阶段：独立的视频片段与检查点事务

建立轻量的 `ExportCheckpoint`／片段清单层，由父进程持有；不依赖工作进程在已经 OOM 后救回当前文件。
记录源身份与内容校验、处理参数／运行库合同、输出编码合同、片段校验，以及下一源帧索引、
有理数 PTS、原始视频起点。使用半开区间定义每段拥有的源帧／输出样本，包含补帧组归属。

片段应在独立可解码的编码边界收尾，排空编码器并核对帧数、PTS、编码参数后再提交。
先完成并验证片段，再原子更新父进程清单；不把已解码／已推理但尚未编码的帧当成完成。
崩溃只丢未提交片段；源或配置变化时拒绝使用旧检查点。保留既有“不覆盖已有输出”的合同。

片段先保存纯视频，结束后用原始源音轨统一封装，避免每段重复音频转码和音频编码延迟累积。
拼接仍须验证全局 PTS、最后一帧时长、HDR／色彩和编码参数。
既有 `concat_video_segments` 可作为基础，但其兼容 MP4 合并能力不等于所有 VFR／GPU 路径已通过续导验收。

本地接入基础：`dlss5tool/video_timeline.py`、`frame_timeline.py`、`video_export.py`、`vfr_mux.py`、`packet_mux.py`。
当前 writer 的 abort／cleanup 会删除本对象未完成临时输出，已提交片段须由新的父进程事务独立持有，
不能只给旧 writer 增加一个 start_frame 参数。

### 第二阶段：检查点保存与进程回收分开调度

频繁保存进度不等于每个片段都必须重新加载模型。正常情况下保留原生会话，
按已提交片段推进；只有达到实际内存压力或经过实测制定的占用预算时，才在安全边界轮换进程。
不要按固定秒数无条件重置时域历史。

在余量仍足够排空编码器和提交片段时提前停止接收新帧。复用 `cfd6022` 已有的所有者退休、
系统实际余量等待、稳定窗口和有限恢复预算；旧 Job／共享帧未退休，不启动新所有者。
工作进程已经失效时回到上一已提交片段，不要求损坏进程继续调用 NGX 完成收尾。
无进展的反复恢复必须暂停，不能因为不断产生短片段而刷新无限失败预算。

独立记录每个处理进程的私有提交与整个任务的总提交／余量；回收后检查真实余量，
不能以新进程启动成功代表全系统资源已释放。保护逻辑保留原安全预留及下一轮启动峰值。

### 第三阶段：恢复历史，但先验证质量

新进程从检查点之前的可靠解码位置开始，保留全局源帧序号／PTS／参数相位，
重放处理链所需的输入历史，丢弃所有已经提交区间的输出；涉及补帧时保留左右源帧邻居及归属。
历史也有内存／缓存预算，不保存整段未压缩视频，不默认转成 RGB8。

32／64／128 帧可以作为实验候选，不能作为通用保证。有限输入重放无法自动证明恢复了 NGX 的全部内部状态。
应与同配置不中断输出比较场景切换、长镜头、慢运动、人脸、颗粒和 HDR 边界，沿用现有质量门槛。
不通过时优先使用实际执行历史 reset 的已验证边界，或扩大重放范围；没有可靠恢复方法的路径不能默认启用自动轮换。
程序重启恢复也必须验证清单读取、源合同核对及未提交片段处理，不能仅因写了 JSON 就标记支持。

### 与上述并行的根因排查

1. 用现有最小 CUDA＋D3D11 负载，在 621.14 重抓外部线程活动及有界分配栈，另设无追踪对照；
   核对线程入口、创建速率与保留量是否对应。线程追踪与堆追踪可分轮，避免监测本身改变斜率而误作性能结论。
2. 针对实际模块路径／版本建立单变量环境对照。只有相关可选模块实际不加载，才能称为有效的缺席对照；
   旧“关闭浮窗开关”及服务重启记录不足以区分各组件责任。安装／卸载／驱动变更另行明确授权。
3. 若新栈匹配驱动线程通知，整理最小复现及版本证据供供应商处理；若变为应用资源不配对，再修对应释放路径。
   应用固定线程池只能减少自己创建的短线程，不能假定能阻止驱动内部线程。
4. 保持原 P0 平台门槛；压力轮换、任务完成、工作集下降均不替代长期 CPU 提交平台。
   继续验证整个任务进程树与系统余量，若进程退出后仍持续增长，单独追查内核／外部所有者。
