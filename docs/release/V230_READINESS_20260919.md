## 新确认的实际发行材料问题

现有 PyAV 18.1.0 本身为 BSD-3-Clause，但 wheel 的 `av.libs` 实际包含 25 个 DLL，
其中包括 libx264/libx265。DLL 返回 `LGPL version 3 or later`，不能由此认定整个 wheel
都只有 LGPL 条款。

已核对固定上游：

- [PyAV v18.1.0 依赖锁定](https://github.com/PyAV-Org/PyAV/blob/v18.1.0/scripts/ffmpeg-8.1.json)
  指向 pyav-ffmpeg 8.1.2-1 Windows x86_64。
- [上游固定构建补丁](https://github.com/PyAV-Org/pyav-ffmpeg/blob/8.1.2-1/patches/ffmpeg.patch)
  将 libx264/libx265 从 EXTERNAL_LIBRARY_GPL_LIST 移到 EXTERNAL_LIBRARY_VERSION3_LIST。
  这解释了为什么加载这些组件时仍返回 LGPL 字样；补丁本身不能替代其他组件的许可。
- [固定依赖源码/哈希](https://github.com/PyAV-Org/pyav-ffmpeg/blob/8.1.2-1/scripts/pkg.py)。
- [FFmpeg 官方分发说明](https://ffmpeg.org/legal.html)要求区分实际启用组件，并提供匹配源码、
  修改和构建说明。这里记录事实，不是对项目整体许可兼容性的法律结论。

另：上游工作流从未固定 MSYS2 工具链包版本；本地 DLL 中 GCC 为 16.1.0，libiconv 1.19、
zlib 1.3.2 可读出。winpthreads 版本资源声明 MIT AND BSD-3-Clause，但不足以确定精确构建源码版本。

因此目前不能把 `packaging_license_review_complete` 改成 true。也不能只提供 PyAV 的 BSD 许可，
或只靠媒体 DLL 的 LGPL 返回字符串跳过检查。GPU 功能验收仍有效；问题是这套具体依赖的发行准备。
